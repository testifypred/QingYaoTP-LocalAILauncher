## 3. headless Edge（CDP）功能自测结果

### 3.5 设置→视觉页签

### 3.6 发送链路（stub 视觉后端；不真正起 sidecar）
- 带图发送时状态栏显示「正在启动视觉模型…」，随后 /api/vision/start 带选中的 model+mmproj
- /v1/chat/completions 请求体：stream=true、images 长度 1 且为 data:image/jpeg;base64、最后一条 user content 为输入文字
- 用户气泡出现 1 张缩略图；助手行 who 旁出现「视觉」徽标；transcript 中 user.images=1、assistant.vision=true；发送后预览清空
- 纯文本发送：请求体不含 images 字段、无视觉徽标（原有链路未变）

### 3.7 启动等待期间不被轮询冲掉
- stub 让 /api/vision/start 延迟 4 秒，第 3.4 秒（跨过 3 秒轮询点）采样：
  状态栏仍为「正在启动视觉模型…」，发送/输入/图片按钮均 disabled，pendingImgs 仍为 1；
  完成后正常出回答、视觉徽标 1 个、请求体带 1 张图、预览清空
- 说明：send() 里用 visionEnsuring 标记让 3 秒 refresh 轮询在启动期间跳过（否则状态会被覆盖、按钮会提前解锁）

### 3.8 运行期错误
- 多次完整加载 + 交互，window.__pageErrors=[]、Runtime.exceptionThrown=0、console error=0

### 3.9 大图补充（Lead 反馈「大图片可能不行」后复测与加固）

复现：4000×3000、11.02MB 手机级噪点 JPEG，旧版 4MB 上限直接拒绝（toast「单张上限 4MB」）。
改造后（app.html 当前版）：

- 11.02MB 大图 → 接受，508ms 完成解码+缩放；发送版 1024×768、406KB，缩略图正常
- 3 张大图（4000×3000 / 4032×3024 / 3000×4000）合计发送版 dataURL 1.19MB；
  模拟 /v1/chat/completions 请求体 JSON = 1.19MB < 后端 4MB 上限
- 8000×6000（48MP）平滑图 → 接受，140ms，发送版 1024×768、19KB
- 伪 12000×8000（96MP）JPEG 头 → 解码前被像素上限拦下：
  toast「图片太大（94MP，上限 80MP），请先缩小再发」
- 21MB 原图 → toast「图片太大（单张上限 20MB）：huge.jpg」
- 回归：64×64 注入/删除、3 张上限、带图发送请求体/气泡/徽标、纯文本无 images、无 pair toast、
  视觉页签/选择记忆 全部复测通过；pageErrors=0、exceptionThrown=0、console error=0

实现要点：
- `MAX_IMG_MB = 20`（原契约 4MB 太小，手机照片常见 5–15MB；属对契约的放宽，已报告）
- 一张原图只解码一次，同时产出发送版与 240px 缩略图（旧实现解码两次）
- 发送版按 `q0.85→0.72→0.62→0.52` 逐档降质量，单张 dataURL 预算 700KB；仍超预算再降到 768px——
  保证 3 张 base64 不会撑爆后端 4MB 请求体
- 解码前后双重像素守卫：先把 JPEG SOF / PNG IHDR / GIF 头里的宽高读出来，>80MP 直接拒绝；
  认不出格式（如 WebP）则在解码后按 naturalWidth×naturalHeight 兜底
- >8MB 原图先 toast「正在压缩大图（11.0MB）…」，避免用户以为没反应

## 5. 未覆盖 / 风险

- 未真实启动/停止 8101 sidecar（测试时 8101 已被外部占用，且会与运行中的文本模型争内存）；
  启停后端的真实行为由 API 探针覆盖，这里只验证前端按钮/状态/请求体。
- 未跑真实视觉问答（慢），发送路径用 fetch stub 校验请求体，真实推理由 probe-vision-api 覆盖。
- 带图提问的「重生成」被禁用（transcript 只存 240px 缩略图，重发会糊）：提示用户重新加图。
- 图片提问不进入 @ 第二意见（sidecar 与文本模型内存互斥），会 toast 说明。
- 会话文件只存缩略图（不存原图），导出 Markdown 不含图片。
- 首屏（footer 隐藏）额外加了 #heroImgBtn/#heroImgPreview；契约只点名 footer 那组，属于可用性补充。
- 视觉回答后文本模型被后端卸载，前端会 refresh + toast 提示重新加载；若用户继续发图可不需要文本模型（已允许）。
- 大图上限从契约的 4MB 放宽到 20MB（用户反馈"大图片不行"）：手机照片可用；单张仍会缩到 ≤1024px。
  若原图 >20MB 或解码后 >80MP（如 1 亿像素原图），会明确 toast 要求先缩小。
- 若「3 张图 + 很长的历史文本」合计超过后端 4MB 请求体，仍可能 413；当前只保证图片部分约 2.1MB 预算。
