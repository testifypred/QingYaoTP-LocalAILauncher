# SmartScreen 与代码签名路线（2026-11-26）

> 现象：用户首次运行下载的 `QingYaoTP AILauncher.exe` 被 Windows SmartScreen 拦（「Windows 已保护你的电脑」）。
> 本文记录**原因、可选方案、成本/限制、建议步骤**（依据 Microsoft 官方文档与各签名服务条款，2026-11 核对）。

## 一、为什么会被拦（官方机制）

Microsoft 官方《SmartScreen reputation for Windows app developers》要点：

1. SmartScreen 看两个信号：**发布者信誉**（是否签名、证书是否可信）与**文件哈希信誉**（这个文件被多少人下载过且无恶意行为）。
2. **未签名**：每个新版本都从 0 信誉开始，必然先弹「Windows 保护了你的电脑」；**自签名证书**与未签名同等。
3. **OV/EV 证书**：首次下载**仍可能弹**（显示发布者名），信誉按证书/哈希累积；**EV 已不再自动免 SmartScreen**（官方明确：不要为 SmartScreen 买 EV）。
4. **Microsoft Store**：微软代签，**永不受 SmartScreen 下载警告**（官方推荐路径）。
5. **Artifact Signing（原 Trusted Signing）**：$9.99/月起、无需硬件 token、CI 集成、Microsoft 做身份验证；签名后信誉同样需要累积。
6. **消费者端没有「提交文件提升信誉」的通道**；信誉只能靠下载量/时间自然累积（数周 + 数百次干净安装）。Portal 提交只用于误报/企业内网。

现状实测（本机 v1.11.1 包）：

| 文件 | Authenticode |
|---|---|
| `QingYaoTP AILauncher.exe` | **NotSigned** |
| `DebugTool.exe` | **NotSigned** |
| `runtime\node.exe` | Valid（上游 Node.js 已签） |

根因：我们自己的两个 exe 没签，浏览器下载 zip 会带 MOTW，解压后 exe 继承 MOTW → SmartScreen 检查 → 未有信誉 → 拦。

## 二、可选方案对比

| 方案 | 成本 | SmartScreen 效果 | 门槛 / 风险 |
|---|---|---|---|
| **A. SignPath Foundation（OSS 免费）** | 免费 | 显示 SignPath Foundation 为发布者；信誉在该证书下累积 | 需申请审核：OSI 许可（Apache-2.0 ✓）、代码公开且活跃、只签自家产物；包内第三方 vendor（llama.cpp/KaTeX/Node/WebView2）需按「系统库/上游未签二进制」规则评估 |
| **B. Artifact Signing（Azure）** | $9.99/月起 | 签名后显示发布者名，信誉累积 | 需 Azure 订阅 + Microsoft 身份验证（企业/个人资格与所在地区要确认；中国大陆可用性需实测） |
| **C. OV 代码签名证书** | 约 $200–400/年 + 硬件 token/云 HSM | 首次仍可能弹（显示发布者名），信誉按证书累积 | 2023 起私钥须在 FIPS 硬件/HSM；性价比低于 A/B |
| **D. Microsoft Store / MSIX** | $19 开发者账号（一次性）+ MSIX 打包改造 | **完全不弹**（微软代签） | 需把便携应用改成 MSIX、过商店政策（本地模型/下载行为需说明）；中长期方案 |
| **E. 不签名（过渡）** | 0 | 必弹，需用户点「更多信息 → 仍要运行」 | 可在 README/使用说明给出指引；winget/7-Zip 解压可减少 MOTW 触发 |

## 三、建议路线

**短期（本周，已做）**：README + 使用说明加入 SmartScreen 说明（更多信息 → 仍要运行；解除锁定；先校验 SHA256）。

**第一优先（免费、最合适 OSS）**：申请 **SignPath Foundation**。

1. 准备材料：仓库地址（public）、Apache-2.0、README/Releases、构建脚本、维护者信息；
2. 说明包内第三方二进制：llama.cpp（MIT）、KaTeX（MIT/OFL）、Node.js（MIT）、WebView2/VC++（微软可再分发），均为上游 OSS/系统库；
3. 通过后：用 SignPath GitHub Action 在 release workflow 里签 `QingYaoTP AILauncher.exe` 与 `DebugTool.exe`（**签完再打 zip**，签名后不要再改文件），时间戳必开；
4. 每版都用同一签名身份 → 证书信誉可跨版本继承（新版本仍可能首弹，但会随下载量下降）。

**备选**：若 SignPath 不通过或周期太长 → 评估 Artifact Signing（先确认地区/身份资格）；OV 证书只在有企业采购需求时考虑；EV 不推荐（不解决 SmartScreen）。

**中长期**：MSIX + Microsoft Store（唯一「永不弹」），或上架 winget（降低 MOTW 触发概率，不改变 exe 签名状态）。

## 四、签名的工程细节（落地时照做）

- 只签自家产物：`QingYaoTP AILauncher.exe`、`DebugTool.exe`；**不要**重签上游 `runtime\node.exe`（它已有有效签名）。
- 签名顺序：编译 → 签名 → 打 zip；签名后任何字节改动都会使签名失效。
- 时间戳：`/tr http://timestamp.digicert.com /td sha256 /fd sha256`（或签名服务自带）。
- 校验：`Get-AuthenticodeSignature` 应为 `Valid`；`signtool verify /pa /all` 通过。
- CI：release workflow 里增加签名步骤（SignPath action 或 Artifact Signing GitHub Action），失败则不发版。
- 发布说明：写明签名状态/发布者名；未签名版本继续保留 SHA256 校验。
